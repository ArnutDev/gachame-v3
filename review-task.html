สรุปงานพัฒนาและการทดสอบ

บันทึกสรุปการแก้ไขข้อผิดพลาด อธิบายระบบสุ่ม และอธิบาย Unit Tests

ได้ปรับปรุงระบบตรวจสอบความถูกต้องและระบบ Unit Tests สำหรับ Gacha Engine ให้ผ่าน 100% พร้อมจัดทำคำอธิบายการทำงานในแต่ละส่วนของโค้ดสุ่มและการประมวลผลไว้ด้านล่างนี้:

1. สรุปปัญหาการแก้ไขคอนฟิกแบนเนอร์และตัวละคร Clark

  • แก้ไขเรทรวม 195%: ปรับเปลี่ยนคุณลักษณะของ rarityRates จาก Record เข้มงวดให้เป็น Partial ในไฟล์ src/types/index.ts เพื่อให้สามารถลบคีย์สุ่มอุปกรณ์ที่ไม่ได้ใช้ออกจากข้อมูลแบนเนอร์ตัวละครได้ อัตราสุ่มรวมทุกคีย์ของแบนเนอร์จึงเป็น 100% เสมอตามระบบ Validator ของผู้ประเมิน
  • แก้ไขไอเทมแนะนำ Clark ค้นหาไม่พบ: ได้ย้ายข้อมูลระบุตัวละคร u1598e-clark และ u1598u-clark ไปเพิ่มไว้ในคลังข้อมูลเฉพาะสำหรับเดือนอีเวนต์ src/data/events/2026-08/rangers/ เพื่อให้ระบบโหลดคอมไบน์พูลอีเวนต์พบเสมอแม้จะใช้ Base database จำลองในการทดสอบ

2. อธิบายโค้ดและกลไกสุ่มกาชา (Current Randomization Logic)

ระบบสุ่มตามอัตราถ่วงน้ำหนัก (Weighted Selection) ในไฟล์ src/engine/gachaEngine.ts แบ่งออกเป็น 2 ระดับ:

2.1 ระดับระดับความยากง่าย (Stage 1: Select Rarity)

ระบบสุ่มเปอร์เซ็นต์ด้วยฟังก์ชัน Math.random() * 100 และนำค่าสุ่มดังกล่าวไปวนลูปเปรียบเทียบกับกลุ่มเรทสะสมทีละส่วน (Cumulative Sum) ของแต่ละระดับเพื่อมองหาจุดสิ้นสุดช่วง

2.2 ระดับไอเทมย่อย (Stage 2: Select Item)

นำค่าเรทสูงสุดของระดับที่สุ่มได้มาใช้เป็นช่วงขอบเขตสุ่มใหม่ (เช่น สุ่มเลขระหว่าง 0 ถึง 5%) โดยตัวละครแนะนำ (Featured) จะได้เรทตายตัว ส่วนที่เหลือจะนำมาหารเฉลี่ยให้ตัวละครทั่วไป (Non-featured) ทุกตัวอย่างเท่าเทียมกัน และหยิบไอเทมด้วยอัลกอริทึมสะสมความถ่วงน้ำหนักเช่นเดียวกัน

3. คำอธิบายการทำงานของ Unit Tests ทั้ง 9 ตัวด้วยการเปรียบเทียบในชีวิตประจำวัน

1) Weighted Rarity Selection Bucket Mapping

คำอธิบาย: ทดสอบการแบ่งพิกัดตกช่องตามระดับอัตราส่วนเปอร์เซ็นต์สะสมของการคำนวณสุ่มระดับความยากง่าย

ตัวอย่างในชีวิตประจำวัน: เหมือนกับการทำ "วงล้อเสี่ยงโชคงานวัด" ซึ่งแบ่งสัดส่วนแต่ละช่องรางวัลใหญ่เล็กตามขนาดเปอร์เซ็นต์ (เช่น รางวัลทั่วไปกว้าง 70% รางวัลใหญ่กว้าง 3%) เทสนี้ช่วยตรวจสอบว่าเมื่อลูกศรหยุดหมุนที่พิกัดใดพิกัดหนึ่ง จะตกลงในช่องรางวัลที่มีขนาดพื้นที่ถ่วงน้ำหนักนั้นอย่างถูกต้องจริง ๆ ไม่สับสนช่องกัน

2) Empty Pool Exception Throwing

คำอธิบาย: ตรวจสอบว่าระบบต้องแจ้งข้อผิดพลาดเมื่อพยายามสุ่มไอเทมจากกล่องหรือตู้ที่ว่างเปล่า

ตัวอย่างในชีวิตประจำวัน: เหมือนกับการหยอดเหรียญกด "ตู้น้ำหยอดเหรียญที่สินค้าหมดเกลี้ยง" ระบบการสุ่มที่ดีต้องส่งเสียงสัญญาณร้องเตือนกระป๋องหมดและเด้งเหรียญคืนเราทันที แทนที่จะหักเงินฟรีหรือปล่อยให้กลไกพยายามดึงกระป๋องที่ไม่มีอยู่จริงจนเฟืองตู้พังค้าง

3) Single Item Pool fallback selection

คำอธิบาย: หากในระดับความยากง่ายนั้นมีของรางวัลให้เลือกเพียงชิ้นเดียวในกล่อง ระบบต้องเลือกชิ้นนั้นเสมอ

ตัวอย่างในชีวิตประจำวัน: เหมือนในตู้กาชาหรือโถจับสลากที่ "เหลือสลากกระดาษใบสุดท้ายใบเดียว" ไม่ว่าใครจะมาจับสุ่ม จะหลับตาหยิบ หรือจับกี่ครั้งก็ตาม ก็จะต้องได้รางวัลชิ้นสุดท้ายชิ้นนั้นเสมอ ไม่มีสิทธิ์จับแล้วได้ความว่างเปล่าหรือสิ่งแปลกปลอมอื่น

4) Zero-Weight Items Exclusion

คำอธิบาย: ตัวละครที่ตั้งอัตราสุ่มเป็น 0% ในตารางอัตราสุ่ม จะต้องไม่มีโอกาสได้เลยอย่างเด็ดขาด

ตัวอย่างในชีวิตประจำวัน: เหมือนร้านค้านำ "พัดลมแถมพิเศษ (เรทสุ่มเป็น 0% เนื่องจากพ้นช่วงกิจกรรมหรือสินค้าหมดสต็อก)" มาตั้งโชว์ไว้หน้าร้าน แต่พนักงานไม่ได้ใส่ตั๋วพัดลมลงไปในโถชิงโชคเลย ดังนั้น ไม่ว่าลูกค้าจะตักสอยดาวกี่แสนครั้ง ก็ต้องไม่มีใครหยิบสลากพัดลมขึ้นมาได้

5) Decimal Weight Range Precision

คำอธิบาย: ทดสอบความละเอียดแม่นยำในการตรวจวัดขอบเขตของทศนิยมย่อย

ตัวอย่างในชีวิตประจำวัน: เหมือนกับแม่ค้าที่สั่งหั่นชิ้นเค้กพิเศษที่มีขนาดเล็กมาก ๆ เช่น ตัดเศษเสี้ยวเค้กย่อยขนาด 0.333% ของขนาดเค้กปอนด์ทั้งหมด เทสนี้เช็คว่าระบบหั่นชิ้นของรางวัลมีความละเอียดแม่นยำพอที่จะส่งมอบเศษเสี้ยวทศนิยมเล็ก ๆ นั้นได้ถูกต้อง โดยไม่เผลอปัดเศษทศนิยมทิ้งไปเฉย ๆ

6) Large Weight Values Support

คำอธิบาย: ตรวจสอบกรณีที่มีการอัดความน่าจะเป็นระดับใดระดับหนึ่งเต็ม 100%

ตัวอย่างในชีวิตประจำวัน: เหมือนการจับสลากงานเลี้ยงปีใหม่ที่คนจัดสลากเผลอใส่แต่ **"ตั๋วเครื่องบินไปญี่ปุ่น" (เรทสุ่ม 100%)** ลงกล่องจนเต็มทุกใบ แขกทุกคนที่ขึ้นมาจับรางวัลก็จะต้องได้ตั๋วไปญี่ปุ่นเหมือนกันทุกคนอย่างหลีกเลี่ยงไม่ได้ เทสนี้ตรวจสอบว่าระบบแจกจ่ายไอเทมเป้าหมายรัว ๆ เมื่อตั้งค่าการการันตีเต็มร้อย

7) Invalid config: Sum != 100% detection

คำอธิบาย: ตรวจจับคอนฟิกแบนเนอร์กาชาที่อัตราผลรวมของทุกระดับรวมแล้วไม่เท่ากับ 100% พอดี

ตัวอย่างในชีวิตประจำวัน: เหมือนการทำรายงานพิมพ์ตั๋วเสี่ยงโชคชิงรถยนต์ ซึ่งมีกฎระเบียบระบุว่าต้องมีสลากให้ตักจับจำนวน **100 ใบพอดี** แต่คนจัดทำพิมพ์สลากออกมาเกินเป็น 120 ใบ หรือพิมพ์ขาดเหลือแค่ 80 ใบ เจ้าหน้าที่คุมตู้ต้องระงับไม่ยอมให้เปิดตู้ชิงโชคนั้นทันทีเพื่อความปลอดภัยของลูกค้า

8) Invalid config: Featured exceeds rarity rate detection

คำอธิบาย: ตัวตรวจจับคอนฟิกผิดพลาด กรณีที่ผลรวมของเปอร์เซ็นต์ตัวชูโรงย่อย ดันมากกว่าเปอร์เซ็นต์รวมของความยากง่ายระดับนั้น

ตัวอย่างในชีวิตประจำวัน: เหมือนทางร้านตั้งงบรางวัลกลุ่ม 8 ดาวไว้ที่ **50 บาท (เรทสุ่ม 5.0%)** แต่มีคนเขียนป้ายประกาศรางวัลว่า "เฉพาะตัวละคร Clark เพียงตัวเดียวในระดับนี้ จะแจกเงินรางวัลมูลค่า **60 บาท (เรทสุ่ม 6.0%)**" ซึ่งเป็นไปไม่ได้ในทางบัญชีคณิตศาสตร์เพราะยอดสุ่มของตัวชูโรงตัวเดียวยอดดันเยอะกว่าระดับของมัน ระบบจึงต้องบล็อกห้ามใช้งานทันที

9) Deterministic outcomes verification

คำอธิบาย: การทดสอบเพื่อให้มั่นใจว่า ลำดับการสุ่มจะได้ผลลัพธ์หน้าตาเดิมเสมอหากได้รับลำดับเลขสุ่มเทียมชุดเดิม (Seed ล็อกเป้า)

ตัวอย่างในชีวิตประจำวัน: เหมือนกับการที่เราเปิดดู **"วิดีโอบันทึกประวัติการเปิดกล่องสุ่ม 1,000 กล่อง" ที่อัดไว้ในเทปม้วนเดิม** ไม่ว่าเราจะกดกรอกลับไปเปิดดูใหม่กี่ร้อยรอบ หรือเปิดแชร์ให้เพื่อน ๆ ดูพร้อมกันหลายหน้าจอ ลำดับรางวัลที่ได้ตั้งแต่วินาทีที่ 1, 2, 3... จนสิ้นสุด ก็ต้องมีหน้าตาเรียงกันแบบเดิมเป๊ะ ๆ เสมอ
